# API Documentation

Full interactive docs (OpenAPI/Swagger) are auto-generated by FastAPI at
`/docs` on the running backend. This file covers what autogenerated docs
don't: the *why* behind each design decision.

## Persons & Cases (`/api/v1/persons`, `/api/v1/cases`) — Phase 4

| Method | Path | Roles allowed | Purpose |
|---|---|---|---|
| POST | `/persons` | ADMIN, INVESTIGATOR, DISASTER_RESPONDER | Create a person |
| GET | `/persons` | any authenticated role | List/filter/paginate (`name`, `gender`, `age_min`, `age_max`, `page`, `page_size`) |
| GET | `/persons/{id}` | any authenticated role | Get one person |
| PATCH | `/persons/{id}` | ADMIN, INVESTIGATOR, DISASTER_RESPONDER | Partial update (only fields present in the body change) |
| DELETE | `/persons/{id}` | ADMIN only | Delete (cascades to that person's cases) |
| POST | `/persons/{id}/cases` | ADMIN, INVESTIGATOR, DISASTER_RESPONDER | Create a case for a person |
| GET | `/cases` | any authenticated role | List/filter/paginate (`case_type`, `status`, `person_id`, `page`, `page_size`) |
| GET | `/cases/{id}` | any authenticated role | Get one case |
| PATCH | `/cases/{id}` | ADMIN, INVESTIGATOR, DISASTER_RESPONDER | Partial update (typically `status`) |
| DELETE | `/cases/{id}` | ADMIN only | Delete |

**Why VERIFIER gets read access but not write:** a verifier reviewing an
AI-generated face match needs to see who the case is about and its current
status to make a sensible call — but case management itself isn't their
job, so they can't create/edit/delete.

**Why deletes are ADMIN-only while creates/updates aren't:** deleting a
person or case is destructive and comparatively rare; gating it to ADMIN
adds a deliberate speed bump without slowing down the routine work
INVESTIGATOR/DISASTER_RESPONDER do constantly (creating persons, updating
case status as an investigation progresses).

**Why every mutation writes to `audit_logs`:** `case.status` is a free
string, not a fixed enum (see the comment in `app/models/case.py`) —
nothing in the schema stops a writer from setting an arbitrary value. What
makes that safe is that every create/update/delete on both persons and
cases writes a row to `audit_logs` with the actor, action, and (for
updates) the before/after values — so even though the *set* of valid
statuses isn't enforced yet, every change is fully attributable. A
stricter transition — e.g. requiring an approved `verification_records`
row before a case can move to a "confirmed identified" status — is a
Phase 15 concern, once the verification workflow exists to gate it.

## Authentication (`/api/v1/auth`) — Phase 3

| Method | Path | Auth required | Purpose |
|---|---|---|---|
| POST | `/register` | none | Self-register as INVESTIGATOR, DISASTER_RESPONDER, or VERIFIER |
| POST | `/register-admin` | ADMIN | Create an account with any role, including ADMIN |
| POST | `/login` | none | Exchange email+password for an access+refresh token pair |
| POST | `/refresh` | none (refresh token itself is the credential) | Exchange a valid refresh token for a new pair (rotates — old one is revoked) |
| POST | `/logout` | none (refresh token itself is the credential) | Revoke a refresh token |
| GET | `/me` | any authenticated user | Return the caller's own profile |

**Why public registration can't grant ADMIN:** this platform handles
sensitive case data, so the highest-privilege role should never be
reachable from an anonymous HTTP request. `RegisterRequest.role` is a
3-value enum (no ADMIN option) — Pydantic rejects `"role": "ADMIN"` with a
422 before the request logic even runs. Creating the first ADMIN account is
done via `database/seeds/seed.py`; creating further ones requires an
existing ADMIN to call `/register-admin`.

**Why login doesn't distinguish "no such user" from "wrong password":**
returning different errors for each lets an attacker enumerate which
emails are registered. Both cases return `401 Incorrect email or password`.

**Why refresh tokens rotate:** each successful `/refresh` call revokes the
token that was just used and issues a new one. A refresh token is
effectively single-use. This limits the damage of a stolen refresh token —
once the legitimate client rotates past it, a replay of the stolen token
fails immediately rather than continuing to work until it expires.

## Authorization (RBAC)

Every protected route depends on `require_roles(*allowed_roles)`
(`app/core/deps.py`). It:
1. Validates the JWT access token (signature, expiry, `type == "access"`).
2. Loads the user fresh from the database (not from anything cached in the
   token) and checks `is_active`.
3. Checks the user's *current* role in the database against the allowed
   list.

Step 2/3 checking the database on every request — rather than trusting the
`role` claim embedded in the JWT — means a role change or account
deactivation takes effect on the very next request, not only once the
(short-lived, ~30 min) access token expires. The `role` claim is still
included in the token for the frontend's convenience (so it can show
role-appropriate UI without an extra request), but it is never the basis
for a server-side authorization decision.

## RBAC verification endpoints (`/api/v1/rbac-demo`) — Phase 3 only

`admin-only`, `investigator-only`, `disaster-responder-only`,
`verifier-only`, `any-authenticated`. These exist solely to prove the
authorization dependency works correctly per role before any real feature
endpoints exist to protect. **Remove or repurpose once Phase 4+ lands** —
persons/cases/verification/admin endpoints will use the same
`require_roles()` dependency for real.
